# Background Web Push: implementation draft and activation gates

This is **disabled source code, not a working production notification service**. No credentials were created, SQL applied, scheduler installed, function deployed or notification permission requested. This stays in the existing web app; the user has parked the separate native companion until web v1 is polished.

## Files and behavior

- `supabase/push-foundation/core.ts`: validated settings/provider subscriptions; owner-specific task planning; morning/evening/deadline-day/custom task candidates; quiet hours; durable-claim dispatcher adapter.
- `supabase/push-foundation/api.ts`: owner-bound subscription/status/preferences/unsubscribe actions. Owner comes from verified authentication, never request JSON. Custom task IDs must exist in that owner's workspace.
- `supabase/push-foundation.sql`: **un-applied** tables with RLS enabled and no public/anonymous/authenticated grants. Only the server service-role adapter can access subscription/delivery rows. Existing workspace ownership/schema is unchanged. Disposable PostgreSQL-WASM checks passed (see COMPLETION_STATUS.md); real Supabase/PostgREST and multi-connection concurrency remain unverified.
- `supabase/functions/daybook-push/index.ts`: draft Edge adapter, independently verifies user JWT with `getUser`, restricts browser origins, validates push-provider endpoints, pins library versions and filters every user operation by verified owner. `/dispatch` separately requires its private server-only secret and rejects browser Origin requests.
- `web/push-client.ts`, `PushReminders.tsx`: UI is inert until both public activation flags exist. Permission is requested only by a direct click on Enable. Browser session token is pinned and owner rechecked, never sent to an arbitrary configured host. Before sign-out, local unsubscribe runs even if the server is offline; uncertain cleanup is explained, not silently counted as success. The app still permits sign-out if the browser cannot confirm cleanup, with a device-settings warning.
- `web/public/sw.js`: generic lock-screen content, no task data rendered, no payload-provided links followed, click opens/focuses only the app's own origin/scope. No private data caching, fetch interception or forced worker takeover.
- `supabase/push-foundation/scheduler.sql.example`: review-only one-minute Cron invocation. Never run during this task.

### Exact delivery semantics

Each device has separate preferences. Morning/evening and aggregated deadline-day alerts use its selected IANA timezone; custom task alerts store an explicit UTC instant selected using the device's local-time date input. Tasks scheduled in the same UTC minute are coalesced into one generic notification; task details are reviewed in the app, not repeated on the lock screen. Completing/deleting a task or removing/rescheduling its custom alert suppresses future candidates. Settings/task existence are rechecked immediately before the atomic send claim, but an already in-flight push cannot be recalled.

Quiet hours suppress, rather than defer, matching alerts. Equal quiet start/end disables quiet hours. Candidate lateness is less than 15 minutes; older missed alerts are not replayed. Daily keys deduplicate a repeated DST hour. A nonexistent DST wall time is skipped. Changing a daily time after it was already attempted does not create a second same-day event.

The database primary key claims one automatic attempt per subscription/event before transmission. This avoids duplicate automatic retries after an uncertain provider outcome; it can sacrifice a notification if a process dies after claiming. Provider 404/410 prunes expired subscriptions. Explicit provider failures are recorded rejected; transport uncertainty is recorded unknown; neither is automatically retried in this draft. `accepted` means provider acceptance, **not confirmed display or delivery**. Review retry/operational policy before activating any user-critical reminders.

Provider host allowlist is deliberately narrow: Apple Push, FCM and Mozilla Web Push. Unsupported browsers/providers fail closed rather than allowing arbitrary outbound URLs. The dispatcher rotates oldest-checked devices in batches of at most 100, with a 35-second budget checked before each candidate/claim, a 10-attempt per-device cap, and explicit backlog reporting. Supabase HTTP calls time out after 5 seconds; one in-flight provider call may take up to 10 seconds. Unattempted events are not preclaimed. An owner-locked SQL transaction enforces 10 devices per account; a service-role-only atomic limiter caps 20 mutations per owner/minute. None of this replaces load testing or abuse protection for public multi-user signup; a sustained backlog needs capacity tuning to stay within the 15-minute reminder window. SQL concurrency correctness still requires staging tests.

## Activation checklist (approval required, not executed)

1. Independent code/security review; create a real migration using the Supabase CLI in an approved environment. Verify SQL/RLS on staging with two users, including endpoint collisions, forged ownership and deletion. Run database advisors. Keep database grants restrictive; don't expose subscription endpoints or keys to anonymous clients.
2. Review and lock the actual Deno dependency graph in the target runtime. The adjacent npm audit lock records pinned libraries but does not replace a Deno deployment lock. Run `deno check`/Edge local execution and end-to-end crypto/provider checks. This environment has no Deno/SQL runtime; these checks have not run.
3. Obtain explicit approval before generating/configuring persistent VAPID credentials and dispatcher secret. Private key, dispatcher secret and Supabase service-role credential remain server-side. Configure server environment: `DAYBOOK_PUSH_ENABLED=true`, `DAYBOOK_VAPID_PUBLIC_KEY`, `DAYBOOK_VAPID_PRIVATE_KEY`, `DAYBOOK_VAPID_SUBJECT` (a valid public contact URI), `DAYBOOK_PUSH_DISPATCH_SECRET`, and exact comma-separated `DAYBOOK_PUSH_ALLOWED_ORIGINS`. Supabase's standard URL/service-role server environment must also be present.
4. Review the dedicated function gateway auth configuration. The dispatcher secret is not a user JWT. If using this combined endpoint, its gateway `verify_jwt` needs explicit configuration while the handler's independent user `getUser` verification and constant-work secret comparison remain mandatory. Do not weaken any existing endpoint to make a deployment work. Alternatively split into separate authenticated-user and scheduled-server functions before activation.
5. Approve deploying the new function/schema and scheduling the job; store scheduling values in server-side Vault, not source. Do not expose dispatcher secret in a public app flag, repository or browser. Read current quota/pricing and verify failure monitoring before scheduling.
6. Only after staging acceptance, set public frontend flags `VITE_DAYBOOK_PUSH_ENABLED=true` and `VITE_DAYBOOK_VAPID_PUBLIC_KEY` to the matching public VAPID key. Neither private key nor any Supabase service-role key belongs in Vite variables. Ensure the deployed service worker/manifest match the target origin.
7. User opts in via Enable on the actual device. iPhone/iPad requires a supported installed Home Screen app; permission prompt must originate from the tap. Test active/closed/locked devices, denied/revoked permission, sign-out offline, switching accounts, missed jobs, DST, quiet hours, completion/reschedule, repeated dispatch, 404/410, timeout and failed backend cleanup. Do not claim live notifications until these pass.
8. A custom-domain move requires fresh install/login/subscription on the new origin. Disable old-origin subscriptions/installations explicitly. There is no automatic cross-origin migration.
